## クイック変換表

SKILL.md の検出スキャン時に最初に当てる短い置換ルール集。詳しい例は次節以降。

### A. 語彙レベル — 短い置換ルール

| 検出パターン                 | 変換方針                                                             |
| ---------------------------- | -------------------------------------------------------------------- |
| 「これにより」               | 「そのため」「その結果」「おかげで」など文脈に合う接続に。または削除 |
| 「〜することができます」     | 「〜できます」                                                       |
| 「〜において」               | 「〜で」「〜では」                                                   |
| 「〜を実現します」           | 具体的に何をするか書く                                               |
| 「〜の最適化」「最適な」     | 具体的に何が良くなるか書く                                           |
| 「本質的な」「革新的な」     | 削除するか、具体的な説明に置き換え                                   |
| 「効果的な」「重要な」       | 何がどう効くのか具体的に                                             |
| 「活用する」「leverageする」 | 「使う」「取り入れる」                                               |
| 「提供する」「サポートする」 | 具体的な動作に（「教える」「手伝う」「届ける」等）                   |
| 「確保する」                 | 「取る」「用意する」「押さえる」                                     |
| 「促進する」                 | 「進める」「後押しする」                                             |
| 「〜する必要があります」     | 「〜しなければならない」「〜すべきだ」（または削除して直接書く）     |
| 「まず最初に」               | 「まず」（重複削除）                                                 |
| 「大幅に」「完全に」「非常に」 | 定量的な表現に（「30%減った」「全件対応した」等）。無理なら削除    |
| 「必要に応じて」             | どんな場合に必要か具体的に書く。書けないなら削除                     |
| 「極めて重要な」「計り知れない」 | 具体的な数字・事実に置き換える。盛りすぎを削る                   |
| 「浮き彫りにしており」       | 具体的に何が見えたか書く                                             |
| 「今後の展開が注目されます」 | 削除するか、自分の予測を書く                                         |
| 「注目に値する」             | なぜ注目したか1文で書く                                              |
| 「重要な示唆を与えている」   | 何の示唆か具体的に書く                                               |

### B. 構造レベル — 短い置換ルール

| 検出パターン                       | 変換方針                                                   |
| ---------------------------------- | ---------------------------------------------------------- |
| 「〜です。〜です。〜です。」連続   | 文の長さを変える、文をつなぐ、「〜だろう」「〜かもしれない」等を混ぜる。体言止めは決め台詞になりやすいので使わない |
| 「さらに」「また」「加えて」の連続 | 1文章に3回以上出たら多すぎ。半分は削除して文の流れで繋げる |
| 「まず」「次に」「最後に」の列挙   | 必要な場合のみ残す。読み手が自然に順序を追える場合は削除   |
| 「一方で」「しかしながら」         | 「ただ」「でも」「けれど」など文体に合うものに             |
| 段落冒頭が毎回接続詞で始まる       | 接続詞なしで始まる段落を増やす                             |
| 全ての文がほぼ同じ長さ             | 文の長さを混ぜる。短い文は事実を述べる文に限り、決め台詞の断片（J）にしない |
| 全角ダッシュ（——）で補足を挟む     | カッコまたは読点に置き換える（ChatGPT最大の書式癖）        |
| 何でも3つにまとめる（三点セット）   | 本当に3つなら3つ。4つあるなら4つ書く。1つでもいい         |
| 「〜ではない。〜だ。」などの否定対比 | 1回でも書き換える。変種と残してよい条件は `negation.md`  |
| 主語を毎文繰り返す                 | 日本語は主語省略が自然。「このツールは〜。このツールは〜。」→主語を省いて繋げる |
| 300字以下のセクションに小見出し     | 見出しを減らす。読者が自然に読める流れを優先               |

### C. 意味レベル — 短い置換ルール

| 検出パターン                   | 変換方針                                   |
| ------------------------------ | ------------------------------------------ |
| 「一般的に〜」「多くの場合〜」 | 削除するか、具体的な条件に置き換え         |
| 「〜が期待されています」       | 誰が期待しているのか明示するか、断言に変更 |
| 「状況によって異なります」     | どんな状況でどう異なるのか具体的に         |
| 「本記事では〜を解説します」   | 削除（読めばわかる）                       |
| 「結論から言うと」             | 削除して結論をそのまま書く                 |
| 「〜と言えるでしょう」         | 断言できるなら断言する                     |
| 「〜ではないでしょうか」       | 言い切る                                   |
| 「業界の専門家によると」等の曖昧な出典 | 具体的な出典を出すか、自分の意見として書く |
| データ後の「〜を示しており」「〜を物語っています」 | その文を丸ごと削除。読者に解釈を委ねる |

## A. 語彙レベル

### 「これにより」の置き換え

人間の文章ではほぼ使われないのに、生成AIの文章では異常に頻出する。

**例1:**
- AI: 「新しい管理システムを導入しました。これにより、業務効率が30%向上しました」
- 自然: 「新しい管理システムを導入した結果、業務効率が30%上がった」

**例2:**
- AI: 「研修プログラムを刷新しました。これにより、社員の満足度が改善しました」
- 自然: 「研修プログラムを刷新したところ、社員の満足度が上がった」

**例3（削除パターン）:**
- AI: 「APIを統合しました。これにより、データの一元管理が可能になりました」
- 自然: 「APIを統合して、データを一元管理できるようにした」

### 「〜することができます」→「〜できます」

**例:**
- AI: 「このツールを使用することで、作業時間を短縮することができます」
- 自然: 「このツールを使えば、作業時間を短縮できます」

### 抽象動詞の具体化

| AI的表現 | 自然な表現の例 |
|---|---|
| 「サポートする」 | 手伝う、助ける、支える、面倒を見る |
| 「提供する」 | 届ける、渡す、出す、用意する |
| 「活用する」 | 使う、取り入れる、役立てる |
| 「実現する」 | 作る、始める、叶える、形にする |
| 「確保する」 | 取る、押さえる、用意する |
| 「促進する」 | 進める、後押しする、広げる |
| 「最適化する」 | 調整する、整える、合わせる |
| 「強化する」 | 鍛える、補う、厚くする |
| 「構築する」 | 作る、組み立てる、立ち上げる |
| 「展開する」 | 広げる、始める、進める |

**例:**
- AI: 「弊社はお客様のビジネスをサポートし、最適なソリューションを提供します」
- 自然: 「お客様の業務に合った仕組みを一緒に作ります」

### 抽象形容詞の具体化

| AI的表現 | 変換方針 |
|---|---|
| 「本質的な」 | 何が本質なのか具体的に書く。書けないなら削除 |
| 「革新的な」 | 何がどう新しいのか書く |
| 「効果的な」 | 何にどう効くのか書く |
| 「重要な」 | なぜ重要かを書くか、削除して直接述べる |
| 「最適な」 | 何に対して最適かを書く |
| 「包括的な」 | 何を含んでいるかを列挙する |
| 「戦略的な」 | 具体的にどんな狙いか書く |

### 意義の過剰強調

**AI:**
> この取り組みは、業界全体のDX推進において極めて重要な役割を果たしており、その意義は計り知れない。

**自然:**
> この取り組みで、社内の申請処理が3日から4時間に縮まった。

「重要な」「極めて」「計り知れない」を消して、具体的な数字・事実に置き換える。

### 定型評価語

以下が出てきたらほぼ確実にAI生成。すべて書き換え対象:

| NGワード | 置き換え方 |
|---------|-----------|
| 浮き彫りにしており | 具体的に何が見えたか書く |
| 今後の展開が注目されます | 削除するか、自分の予測を書く |
| 多面的な / 包括的な / 画期的な | 何がどう多面的なのか具体化 |
| 注目に値する | なぜ自分が注目したか1文で |
| 重要な示唆を与えている | 何の示唆か具体的に |

### 偏愛語

AI が好んで撒く語。1 つの文章に複数出たら疑い、具体的な事実に置き換えるか削る。

- 泥臭さ、手触り、解像度、熱量、本質、営み、文脈、土台、鍵となる
- 真理、美学、境地、矜持のような大げさな語で、個人の経験を膨らませる使い方
- 「示している」「物語っている」「収斂する」のような翻訳調の動詞

## B. 構造レベル

### 語尾の単調さを直す

**AI（単調）:**
> リモートワークが普及しています。多くの企業が導入しています。
> 生産性の向上が報告されています。課題も指摘されています。

**自然（リズムあり）:**
> リモートワークが広がり、導入する企業は増え続けている。
> 生産性が上がったという報告がある一方で、評価制度や雑談の減り方に課題が出ている。

語尾のバリエーション:
- 「〜だ」「〜である」（断定）
- 「〜だろう」「〜かもしれない」（推量）
- 「〜わけだ」（説明。「〜のだ」は否定対比の「〜のではない。〜のだ」になりやすいので控える）
- 文をつないで長さを変える（「〜し、〜した」）

体言止めと倒置は決め台詞に見えやすいので、語尾を変える手段として使わない（J を参照）。

### 接続詞の過剰使用を直す

**AI（接続詞だらけ）:**
> まず、目標を設定します。次に、現状を分析します。
> さらに、課題を洗い出します。そして、解決策を検討します。
> 最後に、実行計画を立てます。

**自然:**
> 目標を決めたら、現状とのギャップを確認する。
> 課題が見えてきたところで解決策を考え、実行計画に落とし込む。

原則: 1文章に3回以上出たら多すぎ。接続詞は段落に1つあれば十分。文の配置と内容で流れを作る。

### 全角ダッシュ（——）

ChatGPT最大の書式癖。日本語でemダッシュで補足を挟むのは英語の直輸入。

**AI:**
> Claude Code——Anthropicが開発したCLIツール——を使えば

**自然:**
> Claude Code（AnthropicのCLIツール）を使えば

### 三点セット強制

AIはあらゆるものを3つにまとめたがる。メリット3つ、ステップ3つ、ポイント3つ。

**AI:**
> 3つのポイントにまとめると: 速度、安全性、コスト

**自然:**
> 速度と安全性は改善し、運用もしやすくなった。コストはほぼ横ばいだった。
> （4つ書く。無理に3つに丸めない。2つや1つに削れないかも考える）

### 否定対比

最優先のパターンなので、別ファイル [negation.md](negation.md) にまとめた。変種の一覧、残してよい条件、書き換えの戦略、例を載せている。

**AI:**
> 単なるツールではない。パラダイムシフトだ。
> コストの問題ではない。文化の問題だ。

**自然:**
> このツールを入れてから、レビュー待ちの PR が 1 日で片付くようになった。
> 予算は付いたが、誰がレビューするかが決まっていない。

### 主語の過剰明示

日本語は主語を省略する言語。AIは英語の癖で主語を毎文入れる。

**AI:**
> このツールは高速です。このツールはセキュリティも強固です。このツールは無料で使えます。

**自然:**
> 高速で、セキュリティも強固なうえ、無料で使えます。

### 見出しの過剰構造化

AIは短い文章でもh2/h3で細かく区切りたがる。

原則: 300字以下のセクションに小見出しは不要。読者が自然に読める流れを優先する。

## C. 意味レベル

### 安全クッション表現を削る

**AI:**
> 一般的に、プログラミング学習は継続が重要だと言われています。
> 多くの場合、初心者は3ヶ月程度で基礎を習得できると考えられています。

**自然:**
> プログラミングは続けないと身につかない。
> 基礎が身につくまでに、だいたい3ヶ月はかかる。

### 受動態・婉曲表現を能動態に

**AI:**
> この手法は多くの専門家によって推奨されています。
> 効果があると期待されています。

**自然:**
> 多くの専門家がこの手法を薦めている。
> 実際に効果が出ている。

### -ing的付け足し構文

データや事実の後に、AIが勝手に意義を付け足すパターン。

**AI:**
> 売上は前年比120%でした。これは同社の戦略が功を奏していることを示しており、今後の成長が期待されます。

**自然:**
> 売上は前年比120%だった。

読者に解釈を委ねる。「〜を示しており」「〜を物語っています」が続いたら丸ごと削除。

### 曖昧な出典

**AI:**
> 業界の専門家によると、多くの企業がこの手法を採用しています。

**自然:**
> Ahrefsが90万ページを分析したデータでは（具体的な出典）
> あるいは: 自分が見た範囲では、3社くらいがこのやり方をしてる（自分の観察として書く）

出典を出すなら具体的に。出せないなら「出典なし」と認めるか、自分の意見として書く。

## D. AI的な装飾

### 比喩の使いすぎを直す

**AI（比喩過多）:**
> データはビジネスの羅針盤です。AIはその推進力となるエンジンであり、
> 両者は成功への両輪と言えるでしょう。この土台の上に、
> イノベーションという架け橋を築いていく必要があります。

**自然:**
> データを見て判断し、AIで処理を自動化する。
> この2つが揃えば、新しいことを始める余裕が生まれる。

## E. 翻訳調

### 日本語圏の慣用と合わない表現

| AI的（翻訳調） | 自然な日本語 |
|---|---|
| 「あなたのビジネスを次のレベルへ」 | 具体的にどうなるか書く |
| 「ゲームチェンジャー」 | 「大きく変える」「転機になる」 |
| 「ジャーニー」（学習の旅） | 「道のり」「過程」 |
| 「インサイト」 | 「気づき」「発見」 |
| 「ベストプラクティス」 | 「うまくいくやり方」「定石」 |
| 「バリュー」 | 「価値」「良さ」 |
| 「リソース」 | 「人手」「予算」「時間」（具体的に） |
| 「ソリューション」 | 「解決策」「仕組み」「方法」 |
| 「イニシアチブ」 | 「取り組み」「施策」 |
| 「エコシステム」 | 「仕組み全体」「つながり」 |

### 横文字のメタファー

| AI的 | 自然な日本語 |
|---|---|
| 「思考のOSをアップデートする」 | 「考え方を変える」 |
| 「仕事をハックする」 | 「仕事を工夫する」 |
| 「習慣をインストールする」 | 「習慣をつける」 |
| 「マインドをリファクタリングする」 | 「考え方を整理する」 |

技術用語として使う「アップデート」「リファクタリング」はそのまま残す。

### カタカナ語の連続

カタカナが3語以上連続したら疑う。

**AI:**
> ソリューションをレバレッジして、イノベーティブなアプローチでトランスフォーメーションを推進する。

**自然:**
> 既存の仕組みを活かして、新しいやり方で業務を変える。

## F. テンプレ感

### 前置き宣言を削る

**AI:**
> 本記事では、効果的なプレゼンテーションの方法について、
> 5つのポイントに分けて詳しく解説していきます。
> ぜひ最後までお読みください。

**自然:**
> プレゼンがうまくいくコツは5つある。

### 「いかがでしたか？」パターンを削る

**AI:**
> いかがでしたか？今回は〜について解説しました。
> 〜を活用して、ぜひ〜してみてください。

**自然:**
> （まとめの内容をそのまま書く。メタな振り返りは不要）

### 「ステップ」の強制構造化を崩す

**AI:**
> ステップ1: 目標を設定する
> ステップ2: 現状を把握する
> ステップ3: 計画を立てる

**自然（内容に応じて）:**
> まず目標を決める。今どこにいるかがわかれば、あとは計画を立てるだけだ。

番号付きステップが本当に必要な場面（手順書・チュートリアル）では残してよい。
ただし「STEP」という装飾語は不要で、普通の番号付きリストで十分。

### 追従的なトーン

**AI:**
> 素晴らしいご質問ですね！非常に良い指摘です。おっしゃる通りです。

**自然:**
> （削除して本題に入る。褒めるなら具体的に何が良いか書く）

読者に媚びない。

### 説教くさい前置き

**AI:**
> ここで重要なのは〜という点です。〜について理解しておく必要があります。注意すべき点として〜

**自然:**
> （前置きを消して、内容をそのまま書く）

読者は大人なので、何が重要かは自分で判断できる。

## G. Markdown構造

textlint-rule-preset-ai-writing の `no-ai-list-formatting`、`no-ai-emphasis-patterns`、
`no-ai-colon-continuation` に対応するパターン。

### 太字+コロンのリスト項目

**AI:**
> - **パフォーマンス**: レスポンスタイムを50%改善
> - **セキュリティ**: 脆弱性を自動検出
> - **スケーラビリティ**: 水平スケーリングに対応

**自然:**
> - パフォーマンス: レスポンスタイムを50%改善
> - セキュリティ: 脆弱性を自動検出
> - スケーラビリティ: 水平スケーリングに対応

太字を外す。ラベル+内容の形式自体は残してよいが、太字は不要。

### 絵文字プレフィックスのリスト

**AI:**
> ✅ テストが全て通過
> ❌ デプロイに失敗
> 💡 新しいアイデア

**自然:**
> - テストが全て通過
> - デプロイに失敗
> - 新しいアイデア

### 述語+コロン+ブロック要素

**AI:**
> 以下のコマンドを実行します:
> ```bash
> npm install
> ```

**自然:**
> 以下のコマンドを実行します。
> ```bash
> npm install
> ```

述語（動詞で終わる文）の後のコロンは句点に。名詞で終わる場合（「使用方法:」）は許容。

## H. 文体の統一

AI生成文が最もバレやすいポイントの一つが、文体の混在。
リライト作業自体が新たな混在を生まないよう注意が必要。

### です・ます調と、だ・である調の混在

**AI（混在）:**
> Gitのブランチ戦略、なんとなくで運用してない？
> ブランチ戦略を理解することは、チーム開発において不可欠です。
> 定番フローを押さえておこう。

**自然（だ・である調に統一）:**
> Gitのブランチ戦略、なんとなくで運用していないだろうか。
> ブランチ戦略を理解しておくことは、チーム開発で欠かせない。
> 定番フローを押さえておこう。

### カジュアル度の混在

**AI（混在）:**
> めっちゃ便利なツールを見つけました。
> 生産性の向上に大きく寄与するものと考えられます。
> ぜひ使ってみて！

問題: 「めっちゃ」「〜てみて！」（超カジュアル）と「寄与するものと考えられます」（論文調）が同居。

**自然（カジュアルに統一）:**
> めっちゃ便利なツールを見つけた。
> 生産性がかなり上がると思う。
> ぜひ使ってみて！

### 判断基準まとめ

| ユーザー指定 | 文体 | 語尾の例 |
|---|---|---|
| フォーマルビジネス | です・ます + 敬語 | 「〜いたします」「〜ございます」「〜でしょうか」 |
| 一般的なブログ | です・ます（ライト） | 「〜です」「〜ますね」「〜でしょう」 |
| テックブログ | だ・である | 「〜だ」「〜である」「〜してみた」「〜だろう」 |
| SNS/カジュアル | 口語 | 「〜だよ」「〜じゃん」「〜かも」 |

指定がない場合は、入力テキストの多数派の文体に合わせる。

## I. 声を入れる

### パターン除去だけでは空っぽになる

**AI（パターン除去後）:**
> AIツールの活用は今後重要になる。

問題: 定型語は消えたが、書き手の経験も意見も残っていない。

**自然（声を入れた後）:**
> 正直、もうAIなしで仕事するのは無理だと思ってる。

### 体験を入れる

**AI:**
> CI/CDの導入により、デプロイの効率が向上する。

**自然:**
> うちのチームは手動デプロイで月2回やらかしてた。CI/CD入れてからゼロになった。

### 不完全さを認める

**AI:**
> この手法は非常に効果的であり、すべてのプロジェクトに推奨できる。

**自然:**
> 自分のプロジェクトではうまくいった。ただ、大規模なやつで試したことはまだない。

## J. 主体と決め台詞

### モノを主語にした擬人化

モノや抽象概念に人の動詞をさせると、誰が何をしたかが消える。

**AI:**
> データが改善の必要性を示している。課題が浮き彫りになった。文化が醸成される。

**自然:**
> 先月のエラー率を見て、リトライ処理を直すことにした。
> 障害の振り返りで、手順書が古いことに担当者が気づいた。

行為者を主語に戻す。行為者が分からないなら、分からないことを書く。

### 命題型の見出し

見出しを主張の文にすると、各節が小さな演説になる。

**AI:**
> ## 監視は人を信頼することから始まる

**自然:**
> ## 監視の設計

見出しは主題の名前（名詞句）にし、主張は本文に書く。

### 劇的な断片化

体言止めや短い断定を重ねて、決め台詞のように締める形。

**AI:**
> シンプル。それだけ。それが本質だ。
> 答えは、仕組み。

**自然:**
> 手順を 1 つに減らしたら、引き継ぎで迷う人がいなくなった。

断片の代わりに、何をしたらどうなったかを一文で書く。

## K. 読点

LLM の日本語は、短い文にも読点を打つ傾向がある。読点の数を人の文章と比べた定量データは見つかっていないが、GPT の文章を判別する研究では「は＋、」の位置が最も効く特徴だった（Zaitsu & Jin 2023）。短い主題の後や文頭の接続詞の後の読点は公用文の流儀では正しいので、誤りとして扱わず、短い文では省く調整として直す。

### 省く候補

| 検出 | 例 | 書き換え |
|---|---|---|
| 文頭から「は、」までが 5 字以下 | 原因は、設定ミスです。 | 原因は設定ミスです。 |
| 25 字未満の文の読点 | 本件は、来週対応します。 | 本件は来週対応します。 |
| 文頭の接続詞・副詞の後が 20 字以内 | 実は、この設定は使われていません。 | 実はこの設定は使われていません。 |
| 連用中止の連続 | 設定を変更し、再起動し、動作を確認しました。 | 設定を変更して再起動し、動作を確認しました。 |
| 接続詞を足して読点を増やす | また、ログを確認したところ、エラーは出ていませんでした。 | ログも確認しましたが、エラーは出ていませんでした。 |
| 主題と条件節の両方に打つ | ECS では、タスク定義を更新すると、新しいリビジョンが作られます。 | ECS ではタスク定義を更新すると、新しいリビジョンが作られます。 |
| 引用の「と」の直後 | 問題ないと、考えます。 | 問題ないと考えます。 |
| 12 字以下の短い節（「〜前に」「〜とき」「〜ため」「〜なら」など）の後に打ち、その後ろも 20 字以内 | アラームが鳴る前に、人が異変に気づいていた。 | アラームが鳴る前に人が異変に気づいていた。 |

### 残す・足す

本多勝一『日本語の作文技術』の二大原則に従う。

- 長い修飾語が 2 つ以上あるとき、その境界に打つ（重文の境界を含む）
- 語順が逆順になったときに打つ
- 読点を外すと係り先が変わる文には打つ
  - 刑事が血まみれ: 「刑事は血まみれになって、逃げ出した賊を追いかけた。」
  - 賊が血まみれ: 「血まみれになって逃げ出した賊を刑事は追いかけた。」
- 15 字を超える主題や条件節の後、逆接「が、」の後、並列の節の切れ目、名詞の列挙には打つ
- 係り先の曖昧さは、読点より先に語順で直す
  - 「急いで修正した PR をレビューしてもらった。」で、急いだのがレビューの場合は「修正した PR を急いでレビューしてもらった。」と直す
- 一文に読点が 4 個以上あれば、読点を削るより文を分ける（vault の textlint の `max-ten` は 3 個まで）

### 機械チェック

`scripts/check_touten.py` で候補を一覧にする。「」の中も一文として調べる。形態素解析を使わない目安のチェックなので、指摘ごとに上の「残す・足す」に当たるかを確かめる。

```bash
python3 -I ~/.claude/skills/natural-japanese/scripts/check_touten.py <file>
```

文書全体で一文あたりの読点が 1.5 個を超えたら、全体を見直す。閾値（5 字、12 字、25 字、20 字、1.5 個）は目安で、出典のある基準ではない。
