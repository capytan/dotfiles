# Natural Japanese — AI的日本語を自然な日本語に変換する

## このスキルの目的

生成AIが出力する日本語には、人間が書かない特有のパターンがある。
これらは文法的に正しくても「読むと違和感がある」「AI臭い」と感じさせる。
このスキルは、そうしたパターンを体系的に検出・変換し、
読み手にとって自然で、書き手の意図が伝わる日本語に仕上げる。

## 変換の原則

1. **削れるものは削る** — 冗長な表現は短くする。意味が変わらないなら短い方が良い
2. **具体的に言い換える** — 抽象語を具体的な動詞・名詞に置き換える
3. **リズムを作る** — 語尾や文の長さに変化をつけて、読みやすくする
4. **書き手の声を残す** — 過度に書き換えない。元の意図・トーンを尊重する
5. **消した後に声を入れる** — パターン除去だけで終わらない。体験・意見・体温を足す

## 検出カテゴリ N、A〜K

カテゴリ名と検出スコープのみここに置く。具体的なトリガー語・変換例・クイック変換表は [references/patterns.md](references/patterns.md) の対応セクションを参照する。N だけは [references/negation.md](references/negation.md) にある。

- **N. 否定対比（最優先）** — 「XではなくY」「Xではない。Yだ」「単なるX」「XというよりY」「XだけでなくYも」「Xでもない、Yでもない」、末尾の短い否定など。1 回出ただけでも書き換える。残してよいのは、読者が実際に持つ誤解を根拠付きで正す場合、範囲や仕様の限定、否定側にも情報がある場合だけ
- **A. 語彙レベル** — AI頻出ワード・抽象動詞/形容詞・意義の過剰強調・定型評価語・偏愛語の置換または削除
- **B. 構造レベル** — 単調な語尾、接続詞過多、全角ダッシュ（——）、三点セット強制、主語の過剰明示、過剰な小見出し
- **C. 意味レベル** — 安全クッション表現、受動態の婉曲化、データ後の付け足し構文、曖昧な出典
- **D. AI的な装飾** — 比喩の濫用（1文章で1-2個まで）
- **E. 翻訳調** — カタカナ語の3語以上連続、和語で言えるものの英語直輸入、横文字のメタファー（「思考のOSをアップデート」）
- **F. テンプレ感** — 前置き宣言、「いかがでしたか？」、STEP 装飾、追従的トーン、説教前置き
- **G. Markdown構造のAI臭さ** — 太字+コロンのリスト、絵文字プレフィックス、述語+コロン+ブロック要素、見出し内の太字（textlint-rule-preset-ai-writing の `no-ai-list-formatting` / `no-ai-emphasis-patterns` / `no-ai-colon-continuation` 準拠）
- **H. 文体の統一** — 「です・ます」と「だ・である」の混在、カジュアル度・敬語レベル・一人称の不統一
- **I. 声を入れる** — パターン除去後の空っぽさを補う。体験/意見/リズム崩し/不完全さの容認/体温のある結論
- **J. 主体と決め台詞** — モノを主語にして人の動詞をさせる擬人化（「データが示している」「課題が浮き彫りになる」）、主張の形をした見出し（命題型見出し）、体言止めや短文を重ねる劇的な断片化（「シンプル。それだけ。」）、文末に焦点を置く分裂文（「〜したのは X でした」）
- **K. 読点** — 短い主題の後（「原因は、」）、短い文の中、文頭の接続詞の後、短い節の後（「鳴る前に、」）、連用中止の連続（「〜し、〜し、」）に打った読点を省く。長い修飾語の境界、逆順の語順、係り先が変わる箇所には残すか足す。`scripts/check_touten.py` で候補を一覧にできる

文体の判断基準（H）:
- **フォーマルビジネス**: 「です・ます」+ 敬語。「〜いたします」「〜ございます」
- **一般的なブログ**: 「です・ます」（ライト）。「〜です」「〜ますね」「〜でしょう」
- **テックブログ**: 「だ・である」調が主流。「〜してみた」「〜だと思う」
- **SNS/カジュアル**: 「〜だよ」「〜じゃん」「〜かも」

ユーザー指定がない場合は、入力テキストの多数派の文体に合わせる。

業務文書（Notion、Slack、PR、Issue、CfP、社外向けの文書）では、I の口語化（「〜じゃん」「正直〜」）を使わない。声を入れるときは、口調を崩さずに体験・数字・判断の理由を足す。

## 実行手順

1. **入力テキストを通読する** — 全体のトーン・目的・読者を把握する
2. **文体を判定する (H)** — 「です・ます」か「だ・である」か、フォーマル度を確認。ユーザー指定があればそれに従う
3. **N を最初にスキャンする** — `references/negation.md` の正規表現で否定対比を拾い、正規表現に当たらない動詞の短い否定（「迷わない」「困らない」）は目視で探す。残してよい条件に当たらないものをマークする
4. **パターンA〜G、J、K を順にスキャンする** — `references/patterns.md` の対応セクションを参照し、該当箇所をマークする。K は、入力がファイルなら `python3 -I scripts/check_touten.py <file>` の候補から始める
5. **変換を適用する** — 元の意図を壊さないよう注意しながら書き換える
6. **声を入れる (I)** — パターンを消した箇所に、体験・意見・リズムの変化を補う
7. **文体の統一を確認する (H)** — 変換後に文体の混在が生じていないか最終チェック
8. **二重チェック** — 書き換え後の文章に N の正規表現をもう一度かける。否定対比を消した跡に別の決め台詞（体言止め、「それが答えだ」）が入っていないかも見る。読み返して「AIが書いたと感じないか？」を自問し、感じたら該当箇所を再度書き換える
9. **変更箇所を提示する** — 元の表現と変換後の表現を対比して見せる

**エッジケース:**
- AI的パターンが見つからない場合 → 変更不要と伝え、理由を添える
- 1〜2文の短い入力 → 変更点の表のみ提示。全文掲載は不要
- 法務文書・規約など意図的にフォーマルな文体 → このスキルの対象外。ユーザーに確認する

## 出力フォーマット

変換結果は以下の形式で提示する:

```
## リライト結果

（変換後の全文）

## 主な変更点

| 変更前 | 変更後 | 理由 |
|---|---|---|
| これにより、生産性が向上します | そのため、作業時間が半分になります | 抽象→具体、AI頻出語の置換 |
```

変更が少ない場合は変更点の表だけでもよい。変更が多い場合はカテゴリ別にまとめてもよい。
