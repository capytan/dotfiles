# Concise Writing — 冗長な文章を判断と理由に絞る

## このスキルの目的

AI が書いた PR の本文や報告は、リンクした Issue と同じ数字や理由を書き直し、diff が示すことを言い換え、確かめた手順を全部並べることが多い。読む人が知りたいのは、何をするか、何を決めてなぜそうしたか、この後に何をすればよいかの 3 つで、ほかは聞かれたら答えれば足りる。このスキルは文章の量を削って、この 3 つに絞る。

description にない使い分け:
- 「この PR の description は長すぎる」「Issue と重複していないか見て」でも発動する
- 元の文章を残して別に短い要約が欲しいときは使わない。このスキルは元の文章の置き換えを作る
- 残す文の言い回しはなるべく変えない。言い回しの癖は `natural-japanese` で直す

## 残すものと削るもの

一つの基準で決める。読む人がリンク先、diff、ログからは得られず、判断や次の作業に要るものを残し、ほかを削る。

残すもの:
- 判断とその理由のうち、リンク先に無いもの。特に、既存の設定や近くのコードと違う選択の理由
- 読む人がこの後に要る手順と注意（merge や deploy の前後の手作業、確かめる場所、戻し方、次にすること）
- この変更で確かめた証拠（変更の範囲が想定どおりと分かる結果、影響が無いと分かる確認）。リンク先に同じ事実が書いてあっても、確かめた結果は証拠として残す。元の文章にある実行結果の全文（plan、テストの出力）は、長ければ `<details>` に畳んで残す
- 数字のうち判断の根拠になるもの
- リンク、`Fixes #123` のような closing keyword、読む人への依頼、未決の点

削るもの:
- リンク先と同じことの書き直し。リンクを残す。テンプレートが「なぜ」を書くよう求めていても、理由がリンク先にあればリンクで足りる
- 証拠やリンク先を言葉で言い換えた文（plan の結果を箇条書きでなぞる、diff の要約）
- 仕組みの一般論、読む人が知っている前提
- 結論に効かない確認（lint や formatter が通った、同じことを別の角度で確かめた）。前提を確かめただけの項目（作業の前に状態が想定どおりだった、変更の外に差分が無い）は、結果の全文が `<details>` にあれば箇条書きから外す。検証の箇条書きは、変更の範囲と影響の有無が分かる数項目にとどめる
- 作業の経緯、捨てた試み、訂正の枠組み（「最初は〜と考えたが」）。訂正で得た事実は残す
- 同じ理由の繰り返し、前の内容を言い直すだけの前置きとまとめ

迷ったときは、その文を消したら読む人の判断や次の作業が変わるかで決める。変わらないなら削る。

## 手順

### 1. 対象を読む

次の順に探す。

1. 依頼に貼られた文
2. 依頼に書かれたファイルのパス（Read で読む）
3. GitHub の PR・Issue の URL。`gh pr view <URL> --json title,body,closingIssuesReferences` か `gh issue view <URL> --json title,body` で読む。`gh pr edit` や `gh issue edit` で書き換えない。反映するかは利用者が決める
4. 「さっきの返答」「今の下書き」と指されたときは、直前の Claude の返答の本文

読んだら、誰が何のために読む文章かを決める。PR ならレビューする人と merge する人、Issue なら判断する人と直す人、報告なら次の手を決める人になる。

### 2. リンク先と diff を読む

本文の記述と重なっていそうなリンク先（Issue、PR、ADR、報告、ファイル）を `gh` か Read で読む。PR なら `gh pr diff <URL>` も読む。互いに関係しない読み込みは並べて実行する。本文のうち、リンク先や diff から得られることに印を付ける。

PR・Issue なら、リポジトリのテンプレートを CLAUDE.md の決まりのとおりに探して読み、見出しとコメントの役割を確かめる。URL が今の作業ディレクトリと別のリポジトリを指していれば、`gh api repos/<owner>/<repo>/contents/<path> -H "Accept: application/vnd.github.raw"` で読む。

権限が無いなどで読めなかった入力（リンク、diff、テンプレート）があれば、それと重なるかは決められないので、該当する箇所は残し、出力で知らせる。

### 3. 文や項目ごとに決める

文と箇条書きの項目ごとに、残す、削る、リンクに置き換える、ほかの文とまとめる、のどれかに決め、残す以外には理由を一言で控える（削ったものの一覧に使う）。

見出しとテンプレートのコメント（`<!-- -->`）の扱いは、CLAUDE.md のテンプレートの決まりに従う。要らない内容は書かないことも選ぶ。書くことが無くなった節は本文を書かず（削ったものの表に載せる）、見出しはテンプレートが許していれば消し、許していなければ見出しとテンプレートのコメントだけを残す。

### 4. 書き直す

- 残した文の言い回しはなるべく変えず、削った文とのつなぎだけを直す
- 新しい事実、数字、理由を足さない
- 文体（です・ます、だ・である）と、和文と英数字の間の空白は元の文章に合わせる

### 5. 消すと困るものを落としていないか確かめる

- 削ったものに「残すもの」に当たるものが混じっていないかを見直し、あれば戻す
- 残した文が削った文に頼っていないかを確かめる。用語や名前の初出、「上の差分」「前述の」のような指す言葉、番号を直すか、削った文を戻す
- 最後に、書き直した本文だけを読む人になったつもりで読み、判断と次の作業ができるかを確かめる

## 出力の形

`````
## 端的にした本文

````markdown
（書き直した全文。そのまま貼れるよう、フェンスで囲む）
````

## 削ったもの

| 削ったもの | 理由 |
|---|---|
| Summary の障害の件数と背景の 2 文 | リンクした Issue の Problem と同じ |
| pre-commit が通ったこと | 結論に効かない確認 |
| Test plan の 2 項目目 | 1 項目目とまとめた |
`````

- 表には、手順 3 で残す以外に決めたもの（削る、リンクに置き換える、まとめる）を全部載せる。元の文を全部引かず、どの箇所かが分かる短い言い方で書く
- 読めなかった入力は、表の下に書く
- 削るものが無かったときは、本文を出さずにそう伝え、理由を一言添える
